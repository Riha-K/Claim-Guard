01

Elevator pitch (45–60 seconds)

“ClaimGuard is an agentic insurance claim triage assistant. Free-text claims go through a fixed tool graph: I retrieve policy clauses with RAG, run explicit fraud heuristics, and build a document checklist. Only after those tools finish does the LLM write a short recommendation — approve for review, need docs, or escalate — citing the tool evidence. The Streamlit UI shows every tool call so an analyst can audit the path. So it is not a single chatbot answer; it is retrieve, check, decide, then explain.”
Resume one-liner: ClaimGuard: multi-step AI agent for insurance claim triage with RAG policy retrieval, rule-based fraud checks, document checklist tools, and an auditable tool trace.
02

What “agentic” means here

Interviewers asking for LangGraph / MCP / agent frameworks want to hear: planning + tools + grounding + observability. ClaimGuard implements that pattern with a custom fixed graph (easy to defend end to end).

What we do

  • Parse fields from free text
  • Call tools in a defined order
  • Decide recommendation from tool outputs
  • LLM summarizes only from the tool bundle
  • Log every tool input/output (trace)

What we are not claiming

  • Not LangGraph / CrewAI / AutoGen
  • Not MCP servers yet
  • Not a trained fraud neural net
  • Not full insurance underwriting automation
  • Not free-form multi-agent debate
Say this: “I built a transparent tool-calling agent. Production could swap the orchestrator for LangGraph; the tools and RAG stay the same.”

04

The three tools

search_policy

Query Chroma with the claim text. Return top-k chunks with source file + score + truncated text. Grounds coverage answers in markdown KB.

fraud_heuristic

Explicit rules: many claims in 30 days, claim soon after policy start, high amount thresholds, third-party without police report. Returns risk low/medium/high + flags.

checklist

Per claim type required docs (auto vs health). Third-party auto adds police_report. Returns required / provided / missing / complete.

Claim typeCore required docs
auto_collisionclaim_form, driving_license, vehicle_rc, damage_photos, repair_estimate (+ police_report if third party)
health_hospitalizationclaim_form, discharge_summary, hospital_bills, investigation_reports, insured_kyc
Field parse: lightweight regex / keyword extract for amount, days since policy, prior claims, third party, FIR/police, doc tokens. Demo-friendly, not NER production.
05

Knowledge base + RAG

Markdown under knowledge_base/ is ingested into ChromaDB with all-MiniLM-L6-v2. Edit policy text → Reindex in the UI. No fine-tune needed for KB updates.

Files in the KB

  • auto_collision.md
  • health_claims.md
  • fraud_signals.md
  • document_checklist.md
  • triage_rules.md

Why this design

Same pattern as PolicyPilot: retrieve then answer. ClaimGuard adds tools around retrieval so the decision is rule-backed, not “LLM vibes only.”

06

How the recommendation is chosen

Decision logic is in code (not left to the LLM). The LLM only explains.

if fraud.risk == "high": recommendation = "escalate" elif not checklist.complete: recommendation = "need_docs" else: recommendation = "approve_for_review"

escalate

High fraud risk flags (priors, early claim, high amount, missing police on TP, etc.).

need_docs

Required documents missing after checklist.

approve_for_review

Docs complete and risk not high. Still human review, not auto-pay.

08

Honesty — what to say / not say

True: multi-step tool agent, RAG over policy markdown, rule-based fraud flags, checklist-driven need_docs, LLM summary grounded on tools, Streamlit audit trace, local Ollama.

Do not invent: LangGraph, MCP, knowledge graphs, production insurer deployment, trained fraud ML, automatic payouts, legal advice, perfect field extraction.

approve_for_review means ready for a human analyst — not auto-approve payment.

Windflow / agentic roles

Lead with tool graph + observability + RAG. Say you can migrate the graph to LangGraph; tools already exist.

vs PolicyPilot

PolicyPilot = RAG Q&A on CX policy. ClaimGuard = RAG + extra tools + triage decision for claims. Same retrieval idea, more agentic.

09

Likely interview Q&A

Q: Explain your agentic / AI project.
ClaimGuard: claim text → parse fields → search_policy (RAG) → fraud_heuristic → checklist → code picks escalate / need_docs / approve_for_review → LLM writes a short grounded note. UI shows the tool trace.
Q: Why tools before the LLM?
So decisions come from inspectable rules and retrieved text, not a free-form model guess. The LLM’s job is explanation, not inventing risk or coverage.
Q: Is fraud detection ML?
No. Explicit heuristics (priors, early claim, amount thresholds, missing police report). Honest and debuggable. Could later add an ML score as another tool.
Q: How do you update policies?
Edit markdown in knowledge_base/, click Reindex. RAG updates without fine-tuning.
Q: Why not LangGraph?
I wanted a small, fully owned graph I can defend line by line. The pattern matches LangGraph (nodes = tools, state = bundle). Porting is a next step, not a missing idea.
Q: Failure modes?
Bad field parse → wrong claim type or docs. Empty retrieval → weak policy citations. Rules miss novel fraud. Mitigation: show tool outputs, keep human in the loop, expand eval cases.
Q: How is this different from a chatbot?
A chatbot answers in one call. ClaimGuard always runs tools, records a trace, and constrains the recommendation with code. Auditability is the product feature.
10

Eval (12 starter cases)

Manual pass/fail against expected recommendation in eval/test_cases.md. Examples: complete auto TP → approve_for_review; missing police → need_docs or escalate; 2 priors + high amount → escalate; health with only claim_form → need_docs.

Interview line: “I keep a small eval sheet of expected triage labels and score the Streamlit runs by recommendation match.”
